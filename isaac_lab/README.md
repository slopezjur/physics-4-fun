# Isaac Lab track

GPU-parallel training for the same dummy the Godot tracks use. The rig is not re-authored here —
it is *generated* from `Scenes/ActiveRagdoll.tscn`, so the Godot scene stays the single source of
truth for masses, joint limits and PD gains.

Read [`obs_action_contract.md`](obs_action_contract.md) before changing anything. It is the
interface both engines implement, and it is frozen.

## Why this exists alongside `rl/`

The `rl/` track runs 16 Godot processes × 64 bodies over TCP and reaches roughly 4,000 steps/s on
the CPU. This track runs thousands of environments as a single GPU tensor in one process, with no
IPC at all. Same dummy, same objective.

Measured on an RTX 4080 SUPER (16 GB), this task, 12 iterations each:

| `--num_envs` | steps/s | vs Godot | VRAM |
|---:|---:|---:|---:|
| 2,048 | 77,000 | 19× | ~3 GB |
| 4,096 | 110,000 | 27× | ~5 GB |
| 8,192 | 126,000 | 31× | ~8 GB |
| 16,384 | 136,000 | 34× | 14.6 GB |

**4,096 is the default, and it is not the fastest row on purpose.** Beyond it, samples per gradient
update grow 4× to buy 24% more throughput, which normally costs more in PPO convergence than the
raw rate returns. Raise it if a task turns out to be sample-hungry rather than update-hungry.

The trade for all of this is that the dummy stops being 16 rigid bodies wired together by
constraints and becomes one reduced-coordinate PhysX articulation — which is why the asset
pipeline below exists.

## Layout

```
isaac_lab/
├── isaac.ps1                entry point - interpreter, D3D12 flag, checkpoint resolution
├── obs_action_contract.md   frozen Isaac <-> Godot interface  (read this first)
├── RESULTS.md               measured outcomes, including what was thrown away
├── assets/
│   ├── dummy.urdf           generated by tools/tscn_to_urdf.py
│   ├── dummy_rig.json       machine-readable rig contract (joint order, limits, gains)
│   └── dummy.usd            generated by scripts/convert_asset.py
├── exported/                promoted policies, obs[1,143] -> actions[1,36]
│   ├── stand_policy.onnx
│   ├── walk_policy.onnx
│   └── perturb_policy.onnx
├── p4f_isaac/
│   ├── assets.py            ArticulationCfg built from dummy_rig.json
│   └── tasks/
│       ├── stand/           hold an upright, settled pose
│       ├── walk/            follow a velocity command  (inherits Stand)
│       ├── perturb/         stay up through an impulse (inherits Stand)
│       └── run/             fast command + flight phase (inherits Walk)
└── scripts/
    ├── convert_asset.py     URDF -> USD, verified against the rig contract
    ├── diagnose_rest_pose.py  is the body even standing before training starts?
    ├── train.py / play.py   Isaac Lab's rsl_rl scripts, with p4f_isaac registered
    └── evaluate_*.py        per-task gates - see "Judging a checkpoint"
```

Each task **inherits** the one it bootstraps from rather than copying it. That is what keeps the
observation and action layouts identical, which is the precondition for `train.py --init_from` to
load one task's weights into another. It also has a trap: a subclass that overrides
`_get_rewards` must restate the `action_clip` barrier, because overriding replaces the parent's
reward wholesale. Walk hit exactly that.

```
Stand ──┬──> Walk ──> Run
        └──> Perturbation
```

`.gdignore` keeps the Godot editor from scanning any of it, the same way `rl/` and `Tests/` are
shielded.

## isaac.ps1

Every command in this track needs three machine-specific details right, and each fails in a way
that does not name its cause: the interpreter (a bare `python` here is a standalone 3.14 Isaac
cannot use), `--kit_args=--/app/vulkan=false` for anything that renders, and a checkpoint path in
the right form. `isaac.ps1` holds all three.

```powershell
.\isaac.ps1 list                          # what is trained, what is exported
.\isaac.ps1 watch perturb                 # arena, newest run, D3D12 applied
.\isaac.ps1 train stand -Iterations 2000
.\isaac.ps1 train walk -From stand        # bootstrap from stand's newest checkpoint
.\isaac.ps1 eval walk -Speed 0.6
.\isaac.ps1 export run                    # exports and promotes to exported/run_policy.onnx
.\isaac.ps1 convert                       # .tscn -> URDF -> USD
```

`-DryRun` prints the command instead of running it. `-Envs`, `-Iterations`, `-Run`, `-Speed`
override defaults, and anything after `--` is forwarded to Hydra:

```powershell
.\isaac.ps1 train stand -- env.action_scale=0.3 env.rew_effort=-0.05
```

**Checkpoint resolution deliberately skips short runs.** "Newest directory containing a checkpoint"
is the obvious rule and it is wrong: a three-iteration smoke test leaves `model_2.pt` behind and
wins over a 1600-iteration run from an hour earlier. It did exactly that on this script's first
invocation. A run must have reached `-MinIterations` (default 50, rsl_rl's `save_interval`) to be
selected; use `-Run <dir>` to pin one explicitly, or `-MinIterations 0` to accept anything.

## Setup

Everything runs in the `env_isaaclab` conda environment against Isaac Lab 2.3.2 / Isaac Sim 5.1.

**Every command below needs that environment's interpreter.** A bare `python` on this machine
resolves to a standalone Python 3.14 install, which Isaac Sim cannot use at all (it needs 3.11), so
the failure is `ModuleNotFoundError: No module named 'isaaclab'` rather than anything descriptive.
Either activate first:

```bash
conda activate env_isaaclab
```

or call the interpreter directly, which is what the commands below do so they can be pasted without
a prior step:

```bash
D:\Programasnaconda3\envs\env_isaaclab\python.exe -c "import isaaclab; print('ok')"
```

Two install traps worth recording, both of which fail in ways that do not name their cause:

- **`flatdict==4.0.1`** is source-only and its `setup.py` imports `pkg_resources`, which pip's
  isolated build environment no longer provides. Core `isaaclab` therefore fails to build, silently,
  in the middle of `isaaclab.bat --install`, leaving every satellite package installed and the one
  they all import missing. Fix: `pip install flatdict==4.0.1 --no-build-isolation` first.
- **`tensordict` must match torch's ABI.** `rsl-rl-lib` requires `tensordict>=0.7.0` with no upper
  bound, so pip resolves to a build compiled against a much newer torch, and it crashes the process
  with a native access violation at import — no Python traceback. With torch 2.7.0, pin
  `tensordict==0.8.3`.

- **`h5py` must be linked against HDF5 1.x, not 2.x.** This one only breaks the *windowed* app, so
  it can hide behind days of successful headless training. `h5py 3.16.0` links HDF5 **2.0.0**;
  Isaac Sim ships HDF5 1.x in `isaacsim.sensors.rtx`, an extension that loads in GUI mode and not
  in headless. The two `hdf5.dll` files collide and Kit dies with
  `Windows fatal exception: code 0xc0000139` (STATUS_ENTRYPOINT_NOT_FOUND) and no stack trace, part
  way through extension startup. Pin `h5py==3.13.0`, which links HDF5 1.14.6. Import order does not
  help — the mismatch is an ABI break, not a load-order race.

If Isaac Sim ever dies at startup with no traceback, suspect an ABI mismatch from an unpinned
transitive dependency before anything else. Two of the three install traps on this page are exactly
that, and neither named its cause.

To find which one, run the failing command and search its log for `Windows fatal exception`, then
read the Python stack printed immediately below it — that names the module whose C extension failed
even when the native backtrace says `Couldn't get crash stack trace`.

## Measured findings

Things that cost real time to discover, kept here because none of them are visible in the code.

**The action space was the whole game.** Mapping `[-1, 1]` onto each joint's full range — which is
what `JointLimitedActionSpace` does, for good reasons of its own — makes balance unlearnable. The
knee spans 2.7 rad, so a 0.5 action commands a 1.35 rad swing, and against 1600 Nm/rad the
actuator just pins at its effort limit. The action space degenerates to bang-bang. Measured:

| action_scale | mean episode length (480 = full 8 s) |
|---|---|
| 1.0 (full range) | 48 steps — *worse than a zero-action baseline's 168* |
| 0.4 | 452 steps |

Nothing else changed between those rows. Before blaming a reward function, check whether a
zero-action policy outperforms the trained one; if it does, the problem is upstream of learning.

**An unbounded policy mean will drift out of the clip range, and nothing stops it.** The
environment clamps actions to `[-1, 1]`, so once a component is outside, pushing it further changes
nothing that gets executed and therefore costs nothing - PPO's mean wanders off to infinity for
free. Measured on a 4000-iteration Stand run with no barrier:

| | raw \|a\| range | components saturated | joints always saturated |
|---|---|---|---|
| iteration 150 | 0.00 - 0.70 | 0% | 0 / 36 |
| iteration 3999 | 0.01 - 18.26 | 97% | 34 / 36 |

The late policy still scored 100% on the strict standing criterion - it stands, rigidly, because
one bang-bang pose happens to be stable - but it has no graded response left for a disturbance to
act on, and it is a useless parent for Walk or Perturbation. The tell is cheap to check: run the
exported policy on a plausible observation and look at the output range. The fix is the
`rew_action_clip` barrier on `relu(|a| - 1)^2`, which is exactly zero for a healthy policy.

**Zero action must mean the rest pose, not the midpoint of the limits.** The obvious affine map
puts `a = 0` at the centre of each range, which for the knee is −1.25 rad. A freshly initialised
policy outputs ≈0, so the body spawns standing and immediately folds. 22-step episodes, every time.

**`body_pos_w` is the link frame, not the body centre.** This URDF puts each link's frame on its
own joint pivot, so the head reports the *neck* — 14 cm low — and the foot reports the *ankle*. A
reward comparing that against the 1.54 m rest head height maxes out at 0.73 and can never be
satisfied. Use `body_com_pos_w` for anything that means "where is this body".

**A Kit crash reports exit code 0.** The smoke test that "passed" had died in a native access
violation; the crash reporter swallows the status. Grep the log for `Fatal` or `crashreporter`
rather than trusting `$?`.

**`velocity_limit` on an implicit actuator is silently ignored.** Isaac Lab warns that the value
"was not getting used by implicit actuators... we continue to not use it" — so the 20 rad/s rail in
`dummy.urdf` and `assets.py` is decorative. `velocity_limit_sim` is the parameter that actually
binds. It is deliberately *not* set here: switching it on would change the physics partway through
a task series whose checkpoints bootstrap from one another, and the rail was only ever a safety
net against solver blow-ups that have not happened. Set it deliberately, on all tasks at once, or
not at all. `effort_limit` is likewise deprecated in favour of `effort_limit_sim`, but unlike
velocity it *is* still applied.

**`play.py` never exits on its own, and headless that is invisible.** Its main loop is
`while simulation_app.is_running()`, which with no window runs until killed. An export run left
behind an orphan holding 4.5 GB of VRAM that quietly contended with training for 90 minutes -
iteration time drifted 1.00 s -> 1.51 s with nothing in either log to say why. Use
`--export_only` (added here) when the goal is the artefact, and check `Get-Process python` before
blaming the GPU for being slow. `TaskStop`/killing a shell wrapper does **not** kill the Python
child.

**Isaac Sim hangs on shutdown on Windows.** `simulation_app.close()` deadlocks in plugin unload
("USD stage detach not called", "Recursive unloadAllPlugins"). Scripts here end with `os._exit(0)`
after the real work is done and verified.

### The renderer only works on D3D12

Isaac Sim 5.1 / Kit 107.3.3 crashes on the **Vulkan** path with this machine's driver (610.88):
`Windows fatal exception: access violation` on the first rendered frame, immediately after
`Simulation App Starting`, with no Python traceback. It is identical in a native window and in
WebRTC livestream, and survives clearing the shader cache and disabling Nsight Aftermath.

NVIDIA have acknowledged this as a Vulkan regression on newer drivers. 580.88 is their officially
tested version and 591.74 is confirmed working; 595.71/595.79/595.97 are reported broken, and this
machine is newer still. See the [forum thread](https://forums.developer.nvidia.com/t/isaac-sim-5-1-gui-crash-access-violation-on-rtx-5070-ti-blackwell-fixed-by-driver-downgrade-to-591-74/365335).

**A driver downgrade is not needed.** The forum reports come from people running the Isaac Sim GUI
directly, which defaults to D3D12 on Windows. Isaac Lab is different: `apps/isaaclab.python.kit`
line 178 sets

```
vulkan = true # Explicitly enable Vulkan (on by default on Linux, off by default on Windows)
```

which forces the broken path. Overriding it back to the Windows default fixes it outright:

```bash
--kit_args="--/app/vulkan=false"
```

Headless training was never affected, because `isaaclab.python.headless.kit` disables the renderer
entirely — which is why three and a half hours of training ran perfectly before this surfaced.

## Judging a checkpoint

**Do not promote a checkpoint on mean episode length.** Stand terminates only below 0.9 m of head
height or past 70° of tilt, so a policy scoring 470/480 may be crouching, wobbling, or standing on
one leg — the exact failure `UprightTermination` was written to catch, and the reason the Godot
Stand run read as healthy while scoring 36% on the strict criterion.

```bash
D:\Programasnaconda3\envs\env_isaaclab\python.exe isaac_lab/scripts/evaluate_stand.py --checkpoint <abs path to model_N.pt>
```

This scores the criterion ported from `UprightTermination`: head ≥ 1.35 m, tilt ≤ 30°, CoM speed
≤ 0.6 m/s, held continuously for 1.5 s. Read three numbers together:

- **standing success** — the gate.
- **mean head height** — must sit near the 1.540 m rest height. Materially below it and the policy
  is surviving in a crouch, which satisfies tilt and speed while never really standing.
- **mean effort used** — a policy holding itself up on a few percent of its torque limit is
  balancing; one near saturation is bracing, and bracing is what stops transferring when the
  solver underneath it changes.
